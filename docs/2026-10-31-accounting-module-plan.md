4. 세금계산서 작성일과 매출일이 다른 경우: 저장을 막지 않는다. 경고를 표시하고 차이 사유와 증빙을 기록하게 한다. 거래조건, 선수금, 분할공급 등 차이가 정당한 경우가 있기 때문이다.
5. 자기확정 사후 검토: 전표 확정과 월 마감을 같은 사람이 하므로, 월별 확정 전표 목록과 감사 로그로 사후 검토한다.

## 회계 모듈의 목적과 경계

- 목적: 회사가 직접 장부를 작성하는 **원장 시스템**이다. 내부 관리용 보조 장부나 세무사 제출용 보조 자료가 아니다. 전표·원장·시산표가 회사 장부의 원본이 되고, 세무사 프로그램은 이 원본을 export 받는다.
- 경계(1차 범위 밖, 세무사 검토를 거침):
  - 부가가치세·법인세 등 법정 신고서 작성과 제출
  - 세무조정(손금불산입 등)과 법인세 계산
  - 전자세금계산서 발행·수신 연동(홈택스 등)
  - 수출 거래(B/L, 영세율, Incoterms)
  - 제조원가 계산
- FlowDesk는 위 신고·조정에 필요한 원장·집계 자료를 제공하고, 신고 판단은 세무사 검토 결과를 따른다.

## 회계기준 판정

- 권고 기본 회계기준: **일반기업회계기준**(한국회계기준원 제정, 외부감사 대상이 아닌 회사도 적용 가능).
  - 근거: 직접 장부를 작성하는 원장 시스템이므로, 향후 외부감사·금융기관 제출·고객사 납품 시 요구 수준을 충족하는 기준을 기본으로 둔다. 계정과목·인식 원칙을 이 기준에 맞춰 설계하면 더 간단한 기준으로 낮추는 것은 가능하지만, 반대 방향은 재분류가 필요하다.
- 용어: 이 문서는 "K-GAAP"라는 약칭을 쓰지 않고 "일반기업회계기준"으로 표기한다. K-GAAP은 맥락에 따라 일반기업회계기준만을 뜻하거나 중소기업회계기준을 포함한 국내 기준 전체를 뜻하는 경우가 있어 혼동될 수 있기 때문이다. K-IFRS(한국채택국제회계기준)는 상장사 등 의무 적용 대상이 아니므로 검토 대상에서 제외한다.
- 미결(별도 확인 필요):
  - 외부감사 대상이 아닌 중소기업은 **중소기업회계기준**(법무부 고시)을 적용할 수 있다. 이 기준을 선택할지 여부
  - 세무사가 사용하는 최종 계정과목표와 코드 체계
  - 두 항목 모두 세무사와 확인해 확정한다(2-9 체크리스트 1·2).

정리:

- **원화 금액이 Float로 저장된 필드: 28개** (Item 2, FinanceRecord 1, PurchaseRequest 1 + Line 4, Purchase 1 + Line 4, SalesPlan 4 + Line 4, Quotation 3 + Line 4).
- Decimal 금액은 `Purchase`의 외자 5개 필드뿐이다.
- Int로 저장된 금액 필드는 확인하지 못했다. Int 필드는 `sortOrder`, `SlipSequence.nextNumber`뿐이다.

- 금액 Float 필드 대부분이 `@default(0)`이다. 값이 없을 때 DB에는 `0`이 남아 "모름"과 "0원"을 구분할 수 없다.
- 서버 `num()`은 null/undefined/빈 문자열/비유한수를 fallback `0`으로 바꾼다. 예: `app/api/purchases/route.ts` 33~37행. 같은 형태의 함수가 purchase-requests, sales-plans, purchases/[id]에도 있다.

추가 사실:

- 구매 라인 VAT는 `taxType`으로만 결정되고 통화를 보지 않는다. USD/JPY 구매도 `taxType = 과세`이면 라인 금액의 10%가 라인 `vat`로 계산된다. 이 값은 별도 필드인 `importVat`와 따로 저장된다.
- 헤더 합계의 의미가 문서마다 다르다.
  - `Purchase.amount`·`PurchaseRequest.amount`: 라인 `total`(VAT 포함) 합. total이 0이면 supply로 대체한다.
  - `SalesPlan.amount`: 라인 `supply`(VAT 제외) 합이며, 별도로 `vat`·`total`을 저장한다.
  - 근거: `app/api/purchases/route.ts`의 `lineRows.reduce((s,l)=>s+(l.total||l.supply))`, `app/api/sales-plans/route.ts` 74~85행.
- 구매·구매요청·판매계획 API는 클라이언트가 보낸 헤더 `amount`를 그대로 받는다(`body.amount !== undefined ? num(body.amount)`).

### 1-3. 과세/영세/면세(taxType) 저장 형태

- DB: `PurchaseRequest`, `Purchase`, `SalesPlan`, `Quotation`의 `taxType String?`. enum이 아닌 자유 문자열이다.
- 선택지: 화면 상수 `TAX_TYPE_OPTIONS = ["과세","영세","면세"]`가 네 파일에 중복 정의돼 있다(`lib/purchases.ts` 97행, `lib/purchase-requests.ts` 81행, `lib/sales-plans.ts` 81행, `lib/quotations.ts` 8행). 화면 라벨은 "거래유형"이다.
- 서버 검증: 각 route는 `String(body.taxType)` 또는 `optional(row.taxType)`로 저장하며, 목록에 있는 값인지 검사하는 코드는 확인하지 못했다.
- 세율: 과세만 10%이고 영세·면세는 0이다. 영세와 면세를 구분해 다르게 처리하는 로직은 확인하지 못했다.
- 라인 단위 taxType은 없고 문서 헤더 단위다. 한 문서에 과세·면세 품목을 섞을 수 없다.
- 거래처(`Vendor`)에는 `codeType`, `bizRegNo`가 있다. 세금계산서·계산서 같은 증빙 유형 필드는 확인하지 못했다.

### 1-4. accountingReflect 현황

- 위치: `Purchase.accountingReflect Boolean @default(false)`. 구매에만 있다.
- 의미: 코드상 효과는 하나다. `true`이면 외자 통관 필드 수정을 409로 막는다(`app/api/purchases/[id]/route.ts` 116행). 통관 다이얼로그는 이 값으로 입력을 잠근다(`import-customs-dialog.tsx` 45행). 목록에는 "반영/미반영", "통관 잠금"으로 표시된다(`app/purchases/page.tsx` 584·589행).
- 설정 경로:
  - `POST /api/purchases`는 `accountingReflect: Boolean(body.accountingReflect)`(179행), `PATCH /api/purchases/[id]`는 `body.accountingReflect`가 있으면 그대로 저장한다(199~200행). 쓰기 권한(ADMIN/OPERATOR)이 있으면 요청 body로 `true`나 `false`를 넣을 수 있고, `true`에서 `false`로 되돌리는 것도 막지 않는다.
  - 화면 경로: 구매입력 저장 payload는 항상 `accountingReflect: false`를 보낸다(`purchase-form.tsx` 437행). `true`로 바꾸는 화면이나 서버 업무 로직은 확인하지 못했다.
  - `true` 값은 데모·목업 데이터(`lib/purchases.ts` mock 행, `lib/seed-demo.ts` 175행)에만 있다.
- 범위 밖: `accountingReflect = true`여도 삭제, 라인·금액·거래처 수정, 상태 변경은 막지 않는다. 라인·금액 수정 차단은 입고 이력이 있을 때만 별도로 동작한다(1-8 참조).
- 결론: 실제 회계 반영 상태를 나타내는 값이 아니다. 실제로 true가 되는 업무 경로가 없다.

### 1-5. 기존 finance 화면/API

- 모델: `FinanceRecord`(client 문자열, description, `amount Float`, `status paid/pending/overdue`, date, dueDate, `category sales/expense/subscription`).
- API: `app/api/finances/route.ts`(GET/POST), `app/api/finances/[id]/route.ts`(GET/PATCH/DELETE). workspace 권한 검사를 적용했고, DELETE에는 연쇄 검사가 없다.
- 화면: `app/finance/page.tsx`. 메뉴 라벨은 "매출·재무"(`components/layout/sidebar.tsx` 107행)이고 부제는 "매출·입금·미수금을 한곳에서 추적합니다. (데모 데이터)"다. `amount > 0`은 매출/입금, `amount < 0`은 지출로 합산하고 월별 차트를 그린다. 상태는 순환 버튼으로 바꾼다.
- 대시보드(`app/dashboard/page.tsx`)도 같은 FinanceRecord로 입금·미수·연체를 집계한다.
- 연결: 구매·판매·재고와 연결되는 키(거래처 코드, 문서 ID)는 없다. 거래처는 자유 문자열 `client`다.
- 회계 모듈과 겹치는 부분:
  - "매출·재무"라는 메뉴명과 매출·지출 집계가 회계 원장·손익과 의미가 겹친다.
  - 부호 기반 금액(+/−)은 차변/대변 체계와 맞지 않는다.
  - 미수·연체 상태 관리는 회계의 채권 관리와 겹친다.

### 1-6. 재고 원가 정보

- `StockMovement`: 수량(`qty Float`), 거래처, 관련 문서(`relatedType`/`relatedId`)만 저장한다. 단가·금액 필드는 없다.
- `StockBalance`: 수량만 저장한다.
- 입고(`app/api/inventory/receipts/route.ts`)와 출하(`.../shipments/route.ts`)는 수량과 관련 문서만 기록한다. `app/api/inventory/**`와 `lib/inventory-server.ts`에서 `unitPrice/amount/price/cost` 문자열을 찾지 못했다.
- 원가로 쓸 수 있는 값:
  - 입고와 연결된 구매 라인의 `unitPrice`(Float). `relatedType: "purchase"`로 구매 헤더에 연결된다.
  - 품목 기준단가 `Item.inboundPrice`(Float, 기본 0)
  - 외자 구매의 `baseAmount`(Decimal, 헤더 단위)
- 외자 부대비용: 관세 금액 필드는 없다. `importVatBaseAmount`는 신고필증 과세표준(관세 등 포함)이며, 관세 자체를 따로 저장하지 않는다.
- 재고조정(`adjustment`)은 수량만 바꾸고 금액 영향을 기록하지 않는다.
- 결론: 현재 수불은 금액을 추적하지 않는다. 기말재고 금액과 매출원가를 시스템 데이터만으로 계산할 수 없다.

### 1-7. 매출 쪽 금액·부가세·거래처 확정 저장 여부

- 판매계획(`SalesPlan`/`SalesPlanLine`): vendorCode/vendorName, 공급가·VAT·합계(Float), taxType을 저장한다. 상태는 `confirmed/in_progress/completed`이며, 출하 진척은 `outboundStatus`로 별도 관리한다.
- 출하(`StockMovement type=shipment`): 수량, 거래처, `relatedType: "salesPlan"` 연결만 저장하고 금액·VAT는 저장하지 않는다.
- 매출 확정 문서(매출전표·세금계산서 발행 기록)에 해당하는 모델은 확인하지 못했다.
- 견적 → 판매계획 전환은 있다(`Quotation.convertedSalesPlanId`, `SalesPlan.sourceQuotationId`).
- 결론: 매출을 인식할 시점과 그 시점의 확정 금액을 기록하는 문서가 없다. 판매계획 금액은 계획값이며, 출하 후에도 1-8에서 보듯 수정할 수 있다.
- 최신 상태(`a477454` 반영 후): 출하 이력이 있는 판매계획의 **삭제**는 409로 차단된다. 출하 이후 판매계획의 **금액·라인 수정 잠금**과 **출하 시점 금액·VAT 스냅샷**은 여전히 없다.

## 2부. 기획 (제안)

### 2-1. 1차 범위

넣을 것:

- 계정과목 관리
- 수동 일반전표(분개) 입력·조회·확정
- 분개장, 총계정원장, 시산표(합계잔액)
- 거래처 보조원장: 다음 6개 계정에 한해 전표 라인에 거래처를 필수로 받고, 거래처별 잔액과 거래처별 원장 조회를 제공한다.
  - 외상매출금, 받을어음, 외상매입금, 미지급금, 선급금, 선수금
  - 이 외의 계정은 거래처를 선택 항목으로 둔다.
  - 입금·지급 반제(어느 채권·채무를 갚았는지 개별 연결)와 채권 연령분석은 2단계다.
- 기초잔액 이관(운영 기준 1): 2027-01-01자 잠정 기초전표 입력과, 2026 결산 확정 후 차이 조정 → 기초전표 확정·잠금. 거래처별 채권·채무 기초잔액은 위 6개 계정의 보조원장 기초로 함께 이관한다.
- 확정 전표의 수정 차단과 역분개(취소 전표). 처음부터 넣어야 이후 자동분개와 기간 잠금이 같은 규칙을 쓴다.
- 권한(확정):
  - 전표 확정과 월 마감은 시스템 역할(`WorkspaceRole` ADMIN/OPERATOR/VIEWER)과 **별도의 회계 권한**으로 설계한다. 시스템 ADMIN이라고 자동으로 확정·마감 권한을 갖지 않는다.
  - 운영상 두 권한(전표 확정, 월 마감)은 한 명의 담당자에게 함께 부여한다.
  - 전표 초안 작성·수정은 ADMIN/OPERATOR가 할 수 있다. VIEWER는 조회만 한다.
  - 같은 사람이 작성하고 확정하는 자기확정을 허용하되, 월별 확정 전표 목록과 감사 로그(누가·언제 확정·역분개했는지)로 사후 검토한다.
  - 월 마감 기능 자체는 2단계(2-6)이며, 1단계는 확정 권한만 쓴다.
- 재판정: 1단계(계정과목 + 수동 전표 + 확정/역분개 + 분개장·총계정원장·시산표 + 제한된 거래처 보조원장 + 기초잔액 이관)를 유지한다. 1단계만으로 2027-01-01부터 수동 기장이 가능하고, 이후 단계는 이 원장 위에 자동분개·마감을 얹는다.

### 2-3. 전표 유형과 분개

- 1차: 수동 일반전표만 둔다. 입금·출금·대체 구분은 화면 편의일 뿐 저장 구조는 같게 한다.
- 3차 자동분개 후보:
  - 외자 구매: 통관 확정 시 상품·미착품 / 외상매입금, 부가세대급금-수입 / 현금 또는 미지급금
  - 내자 구매: 확정 또는 입고 시점
  - 매출: **출하 시점**(사용자 결정). 다만 아래 선행 조건이 모두 갖춰진 뒤에만 도입한다.
    1. 매출 확정 문서, 또는 출하 시점의 공급가·VAT·거래처·과세유형 스냅샷 저장
    2. 출하 이력이 있는 판매계획의 금액·라인·거래처 수정 잠금(삭제 잠금은 `a477454`로 완료)
    3. 금액 Decimal 전환과 서버 측 공급가·VAT 재계산
  - 매출 전표 금액은 판매계획의 현재 값이 아니라 출하 시점 스냅샷을 원천으로 한다. 계획 문서가 나중에 바뀌어도 이미 인식한 매출이 따라 바뀌지 않게 하기 위해서다.
  - 매출 전표 날짜는 실제 출고일(도착 인수 조건 거래처는 고객 도착일)이다. 시스템 처리일과 별도로 저장한다(운영 기준 3). 거래처별로 "도착 인수 조건" 여부를 지정할 수 있어야 하므로, 거래처 마스터에 이 구분을 추가하는 것이 선행 조건에 포함된다.
  - 세금계산서 작성일이 매출일과 다르면 저장을 막지 않고 경고와 함께 차이 사유·증빙을 기록한다(운영 기준 4). 1단계 수동 매출 전표에도 같은 규칙을 적용한다.
- 원 문서 수정·삭제 규칙(자동분개 도입 시):
  - 기본은 수정 차단이다. 확정 전표가 연결된 원 문서의 금액·거래처·날짜·과세유형 변경과 삭제를 서버가 409로 막고, 화면은 잠금과 사유를 표시한다. 현재 구매의 입고 이력 409 패턴을 같은 형태로 확장한다.
  - 정정이 필요하면 역분개 전표를 만들어 원 전표를 취소한 뒤에만 원 문서 잠금을 푼다. 이미 확정된 전표 자체를 직접 수정하거나 삭제하지 않는다.
  - 이미 잠긴 기간(2-6)에 속한 역분개는 다음 열린 기간 날짜로만 만들 수 있다.
- accountingReflect 확장 여부: 현재 값은 요청 body로 바꿀 수 있어 잠금 근거로 쓸 수 없다(1-4). 자동분개를 도입할 때는 다음 두 가지를 함께 처리해야 한다.
  - 이 값을 "연결된 확정 전표 존재 여부"에서 서버가 파생하도록 바꾼다.
  - POST/PATCH body로 받는 경로를 제거한다.
  - 판매계획에는 같은 수정 잠금이 없으므로 매출 쪽에도 같은 규칙을 새로 적용해야 한다(삭제 잠금은 `a477454`로 적용됨, 수정 잠금은 미구현).
- 차대 균형 강제 원칙:
  - 서버가 저장 트랜잭션 안에서 라인 합계를 정수(원)로 비교하고, `차변 합 = 대변 합`이 아니면 거부한다. 클라이언트 합계를 신뢰하지 않는다.
  - 라인마다 차변 또는 대변 한쪽만 양수로 한다. 0원 라인과 음수는 거부한다.
  - 확정 전표는 append-only로 하고, 수정은 역분개로만 한다.
  - DB 수준 보강(체크 제약 또는 트리거)은 기술 검토 항목으로 남긴다. 애플리케이션 검증만으로 충분한지 판단해야 한다.

### 2-4. 부가가치세

- 계정: 매입 부가세는 `부가세대급금`, 매출 부가세는 `부가세예수금`으로 둔다. 납부·환급 정산 전표는 수동으로 처리한다.
- 수입 부가세 구분: **B안으로 확정**(사용자 결정).
  - `부가세대급금` 아래에 `부가세대급금-일반`과 `부가세대급금-수입`을 별도 계정코드로 둔다. 코드 값 자체는 세무사 계정과목표 확인 후 확정한다(2-9). 같은 계층 의미를 유지하는 한 명칭은 바뀔 수 있다.
  - 수입 부가세 전표 라인에는 계정 구분과 별도로 다음 관리항목을 둔다.
    - 증빙유형: 수입세금계산서 / 수입신고필증
    - 거래처: 세관 등 실제 발행처(물품 공급자인 해외 거래처와 구분)
    - 원 문서 참조: 해당 외자 구매와 신고번호(신고번호 필드가 현재 없으므로 자동분개 단계에서 추가 여부 결정)
- 설계 제약(수입 VAT):
  - `importVat`와 `importVatBaseAmount`는 신고필증의 원화 값을 사용자가 직접 입력한 값이다(1-2). 회계 모듈은 이 값을 재계산하거나 덮어쓰지 않고 그대로 원천으로 쓴다.
  - 외자 구매의 일반 라인 `vat`(`taxType` 과세이면 라인 금액의 10%로 계산됨, 1-2)와 `importVat`를 **이중으로 인식하지 않는다**. 외자 구매의 매입 부가세는 `importVat` 하나만 `부가세대급금-수입`으로 기표하고, 같은 문서의 라인 `vat`는 부가세 계정에 기표하지 않는다.
  - 이 규칙은 자동분개 도입 시 서버가 강제한다. 수동 전표 단계에서는 화면 안내로만 표시하고, 같은 외자 구매 참조로 두 부가세 계정에 동시에 기표되는 경우 경고한다.

- 영세·면세: 현재 세율 차이만 있고(1-3) 신고상 구분 근거(영세율 첨부서류, 면세 계산서)가 없다. 수출이 없으므로(사용자 결정 6) 영세율 매출은 1차 설계 대상에서 제외한다. 1차 수동 전표에서는 과세유형(과세·면세)을 전표 라인 관리항목으로 받는다.
- 원천 문서의 taxType이 자유 문자열이라(1-3) 자동분개 전에 서버 측 허용값 검증이 필요하다.

### 2-5. 재고 원가

후보 평가:

| 방법 | 필요 데이터 | 현 구조와의 적합성 |
|---|---|---|
| 총평균법(월별) | 기간별 입고 금액 합과 수량 합 | 수불에 금액이 없어도 월말에 구매 금액을 집계해 계산할 수 있다. 소량 거래에 적합하다. |
| 이동평균법 | 입고 시점마다 금액 기록, 출고 시점 단가 확정 | 수불 행마다 금액이 필요하다(현재 없음). 과거 수정 시 이후 단가 전부를 다시 계산해야 한다. |
| 선입선출법 | 입고 로트별 잔량·단가 | 로트 개념이 없다. 구현과 검증 부담이 가장 크다. |

- 확정 방법(사용자 결정 8): 현재 세무서에 신고된 평가방법을 세무사에게 확인한 뒤 그 방법으로 확정한다. 계속성 원칙상 신고 방법을 바꾸려면 변경 신고가 필요하므로, 시스템이 방법을 먼저 정하지 않는다.
- 위 표는 신고 방법별 구현 난이도 참고용이다. 신고 방법이 총평균법이면 현 구조에서 가장 구현하기 쉽고, 이동평균법·선입선출법이면 수불 금액·로트 구조가 추가로 필요하다.
- 구현 blocker: 신고 방법 확인 전에는 재고 금액의 회계 연동(수불 금액, 재고자산 잔액 자동 계산)과 매출원가 자동분개를 구현하지 않는다. 그 전까지 매출원가와 기말재고는 수동 결산 전표로 처리한다.
- 추가 전제 조건(어느 방법이든 공통):
  1. 구매 금액이 Decimal로 전환되고 서버가 재계산해야 한다.
  2. 외자 매입원가에 관세·운임 등 부대비용을 넣을 데이터가 필요하다. 현재 관세 필드가 없다(1-6).
  3. 재고조정의 금액 처리 규칙이 필요하다.
- 기초재고: 2026-12-31 재고 금액은 세무사로부터 받은 재고 명세로 기초전표에 이관한다(운영 기준 1). 수량 기초는 기존 재고 모듈 값과 대사한다.

### 2-6. 마감과 기간 잠금

원칙:

- 사업연도는 1월 1일 ~ 12월 31일이다(사용자 결정 5). 회계기간은 1~12월 월 단위로 둔다.
- 월 단위 회계기간을 둔다. 잠긴 기간의 전표 생성·확정·역분개를 서버가 거부한다.
- 월 마감과 잠금 해제는 회계 권한(월 마감 권한) 보유자만 할 수 있다. 시스템 ADMIN 역할만으로는 할 수 없다. 해제 시 사유를 받아 감사 로그에 남긴다. 현재 AuditLog 인프라를 재사용한다.
- 기초전표(2027-01-01자)는 2026 결산 확정과 차이 조정 후 확정·잠금한다. 잠금 전까지는 "잠정" 상태를 화면에 표시한다.
- 자동분개 도입 후에는 잠긴 기간에 속한 원 문서의 수정도 같은 판정으로 막는다.

단계:

1. 1차: 기간 잠금 없이 전표 확정/역분개와 기초전표 잠정→확정 잠금만 둔다.
2. 2차: 월 마감(잠금·해제)과 월별 확정 전표 목록(자기확정 사후 검토용)을 도입한다.
3. 3차: 연 결산 전표(손익 대체)와 이월을 도입한다.

### 2-7. 기존 모듈 영향

  - 기존 테이블과 FK 없이 추가할 수 있어 1차는 additive migration만으로 가능하다고 판단한다. 전표 라인의 거래처 참조는 기존 거래처 마스터를 참조만 한다(기존 테이블 변경 없음).
- 수정이 필요한 기존 테이블·API·화면(3차 이후):
  - 금액 컬럼 Float → Decimal 전환: Purchase/PurchaseLine, SalesPlan/SalesPlanLine, PurchaseRequest/Line, Quotation/Line, Item 단가.
    - 대상: 해당 route 전부, 클라이언트 lib(`lib/purchases.ts` 등), 폼 4종, 현황 화면, 견적 도메인 로직

  - `accountingReflect` 쓰기 경로 제거, 서버 파생으로 변경: `app/api/purchases/route.ts`, `[id]/route.ts`, `purchase-form.tsx`, `lib/purchases.ts`
  - 판매계획 수정 연쇄 검사 추가(출하 후 금액·라인·거래처 잠금): `app/api/sales-plans/[id]/route.ts` PATCH. 삭제 연쇄 검사는 `a477454`로 완료.

  - 거래처 마스터에 "도착 인수 조건" 구분 추가(매출일 판정용)

  - 시드 계정 코드가 전표에 쓰이기 시작하면 코드 체계를 바꾸기 어렵다.

### 2-8. 치명적 위험 (데이터가 쌓인 뒤 되돌리기 어려운 지점)

1. Float 원천 금액을 원장으로 옮기는 것. 소수 오차가 차대 불일치나 1원 차이로 고정된다. Decimal 전환 전에는 자동분개를 금지한다.
2. 클라이언트가 계산한 VAT·합계를 신뢰하는 것(1-2). 원장 금액이 서버 규칙과 다를 수 있다.
3. 요청 body로 바뀌는 `accountingReflect`를 잠금 근거로 쓰는 것(1-4). 회계 반영 여부가 위조·해제될 수 있다.
4. 출하 시점 스냅샷 없이 판매계획의 현재 금액으로 매출을 기표하는 것(1-7). 매출 인식은 출하 기준으로 확정됐지만 판매계획은 출하 후에도 수정할 수 있어, 계획값이 매출로 남거나 이미 인식한 매출이 사후에 바뀐다.
5. 판매계획 수정이 출하·전표와 연쇄되지 않는 것(1-8). 삭제는 `a477454`로 막혔지만, 출하 후 금액·라인 수정은 여전히 가능하다.
6. 계정 코드 체계를 확정하기 전에 전표를 쌓는 것. 재분류 전표가 대량으로 필요해진다.
7. 재고 평가방법을 확정하기 전에 원가 전표를 쌓는 것. 방법을 바꾸면 과거 원가 재계산이 필요해진다.
8. "모름"을 0으로 저장하는 것(1-1). 원가·단가 0이 실제 0원으로 집계된다. 회계 모듈은 미확정 값을 null로 두고 화면에 `-`로 표시해야 한다.
9. 외자 부대비용(관세 등)을 저장하지 않는 것(1-6). 재고 원가가 체계적으로 과소 계상될 수 있다.
10. 외자 구매의 라인 `vat`와 `importVat`를 함께 매입 부가세로 기표하는 것(2-4). 매입세액이 이중으로 공제 대상에 잡힌다.
11. 잠정 기초전표를 확정하지 않은 채 운영하는 것. 2026 결산 확정 차이를 반영하지 않으면 2027년 전체 잔액이 세무사 장부와 어긋난다.
12. 세금계산서 작성일과 매출일 차이를 저장 차단으로 처리하는 것. 정당한 차이(선수금, 분할공급 등)가 있는 거래를 기표하지 못해 장부 밖 처리가 생긴다. 경고와 사유·증빙 기록으로 처리한다.

### 2-9. 세무사 확인 체크리스트와 구현 blocker

사용자가 세무사에게 확인·요청할 항목과, 답을 받기 전까지 막히는 구현 범위:

| # | 확인 항목 | 막히는 구현(blocker) | 확인 전 가능한 범위 |
|---|---|---|---|
| 1 | 계정 코드표와 세무사 사용 프로그램(export 형식 포함) | 표준 계정 시드 코드 확정, 1단계 운영 시작(전표 적재), 세무사용 export 형식 | 계정과목 구조·CRUD·전표·원장 로직 구현과 CI 검증(임시 코드로). 운영 데이터 적재는 불가 |
| 2 | 적용 회계기준(일반기업회계기준 / 중소기업회계기준) | 재무제표 서식·계정 분류 확정(2단계) | 1단계 전체(원장 로직은 기준과 무관) |
| 3 | 신고된 재고평가방법 | 재고 금액 회계 연동, 매출원가 자동분개(4단계) | 매출원가·기말재고 수동 결산 전표 |
| 4 | 2026 결산 확정 시기, 이관 명세 수령(계정별 잔액, 거래처별 채권·채무, 재고, 고정자산) | 기초전표 확정·잠금, 거래처 보조원장 기초잔액 확정 | 잠정 기초전표 입력(2027-01-01 운영 시작 시) |
| 5 | 고정자산·감가상각 현황(자산 목록, 상각 방법·내용연수) | 고정자산 대장·감가상각 자동 계산 범위 결정 | 고정자산 계정 잔액 이관과 수동 상각 전표 |

- 일정상 주의: 2027-01-01 운영 시작을 지키려면 1번(계정 코드표)은 1단계 운영 반영 전에 받아야 한다. 4번은 운영 시작 후 받아도 되지만, 받기 전까지 기초전표는 잠정 상태로 남는다.

### 2-9-1. 사용자 확인 질문(세무사 외)

확정된 항목(목적, 매출 인식, 수입 부가세, 업종, 사업연도, 수출, 사용 시작일, 회계 권한)은 "확정된 사용자 결정"으로 옮겼다. 남은 미결:

1. 은행 거래내역 연동이나 업로드가 필요한지
2. 세금계산서 발행 기록 방식: 발행은 어디서 하는지(홈택스 직접, 별도 프로그램), FlowDesk에 발행 번호·작성일을 기록해야 하는지(작성일-매출일 차이 경고에 필요)
3. 도착 인수 조건 거래처가 현재 몇 곳이고 어느 거래처인지
4. 회계 권한(전표 확정·월 마감) 담당자가 누구인지

참고로 남겨 두는 부수 질문(1차 범위 결정에는 영향 없음):

- 외자 구매의 관세·운임·통관수수료 정보를 어떤 서류로 받는지, 재고 원가에 넣는지(4단계 재고 원가의 전제)
- 기존 "매출·재무"(FinanceRecord) 데이터가 실제 업무 데이터인지 데모인지, 계속 쓸지
- 향후 고객사 납품 시 고객사별로 계정과목표를 다르게 쓸 수 있어야 하는지

### 2-10. 단계와 완료 기준

1단계: 계정과목 + 수동 전표 + 분개장·총계정원장·시산표 + 거래처 보조원장(6개 계정) + 기초잔액 이관 (additive, 기존 테이블 무변경)

- 착수 조건: 구현과 CI 검증은 바로 가능하다. Production 운영 반영(실데이터 적재)은 세무사 체크리스트 1번 완료 후.
- 완료 기준(CI 격리 PostgreSQL에서 검증):
  - 표준 계정 시드(유통업, 제조 계정 없음)
  - 계정 CRUD 중 사용중 계정 삭제 409
  - 전표 저장 시 차대 불일치 400, 0원·음수 라인 400
  - 확정 전표 수정·삭제 409, 역분개로 잔액 원복 read-back
  - 시산표 차변 합 = 대변 합
  - 원장 잔액과 전표 합계 일치
  - 금액 Decimal(18,0) 정수 저장 read-back
  - 보조원장 6개 계정에서 거래처 누락 시 400, 거래처별 잔액 합 = 계정 잔액
  - 잠정 기초전표 입력 → 확정·잠금 후 수정 409
  - 세금계산서 작성일 ≠ 매출일인 매출 전표: 저장은 성공하고 응답에 경고가 포함됨, 차이 사유·증빙 기록 read-back, 사유 미기록 건은 "사유 미기록" 상태로 조회됨
  - workspace 교차 접근 403/404, foreign 데이터 불변
  - VIEWER 쓰기 403, OPERATOR·ADMIN 초안 작성 허용, 회계 확정 권한 없는 ADMIN의 확정 403, 권한 보유자 확정 성공
  - 확정·역분개 감사 로그(행위자·시각) read-back
  - 기존 integration·E2E 전부 녹색, CI pass guard 상향
  - Edison 독립 QA와 제갈량 승인

2단계: 월 마감(기간 잠금) + 재무제표(재무상태표·손익계산서) + 부가세 집계 조회 + 입금·지급 반제 + 채권 연령분석

- 착수 조건: 재무제표 서식은 세무사 체크리스트 2번 확인 후.
- 완료 기준:
  - 잠긴 기간 전표 생성·확정·역분개 거부
  - 월 마감·해제는 회계 마감 권한자만 가능, 해제 사유 감사 로그 read-back
  - 월별 확정 전표 목록 조회
  - 재무제표 합계가 시산표와 일치
  - 반제 후 거래처 미결 잔액 = 보조원장 잔액

3단계: 원천 금액 정비 → 자동분개

- 3a 완료 기준(원천 금액 정비):
  - 금액 컬럼 Decimal 전환 migration을 staging에서 검증(백업, 차이 리포트, rollback)
  - 서버 공급가·VAT 재계산
  - taxType 허용값 검증
  - `accountingReflect` 서버 파생화
  - 판매계획 수정 연쇄 검사(출하 후 금액·라인·거래처 잠금). 삭제 연쇄 검사는 `a477454`로 완료
  - 출하 시점 금액·VAT 스냅샷 또는 매출 확정 문서
- 3b 완료 기준(외자 구매 자동분개부터):
  - 원 문서 수정·삭제 409
  - 역분개 후 해제
  - 차대 균형과 원 문서 금액 일치를 runtime 검증
  - 외자 구매는 `importVat`만 `부가세대급금-수입`으로 기표되고 라인 `vat`는 부가세 계정에 기표되지 않음을 runtime 검증
- 3c 완료 기준(출하 기준 매출 전표):
  - 3a의 판매계획 수정 잠금과 출하 시점 스냅샷이 선행 완료
  - 매출 전표 금액이 출하 스냅샷과 일치하고, 이후 판매계획 변경 시도가 409로 막히는지 runtime 검증
  - 매출 전표 날짜 = 실제 출고일(도착 인수 조건 거래처는 도착일), 시스템 처리일과 별도 저장 read-back

4단계: 재고 원가(신고된 평가방법) + 매출원가 자동 계산

- 착수 조건: 세무사 체크리스트 3번(신고 재고평가방법) 확인과 2-5의 공통 전제 조건 충족.
