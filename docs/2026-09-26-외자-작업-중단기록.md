## Production migration 적용 절차 — 승인 전 실행 금지

Production 적용이 별도 승인된 경우에만 사용자가 직접 실행한다. 연결 문자열·비밀번호·secret은 기록하거나 출력하지 않는다.

1. Direct connection으로 Production 대상과 백업 상태를 확인한다.
2. `npx prisma migrate status` 실행 결과를 저장한다.
3. 승인된 migration을 timestamp 순서대로 모두 적용한다. 현재 순서는 `00000000000000_baseline` → `20260925030000_audit_log` → `20260925050000_import_purchase_fields`이며, `npx prisma migrate deploy`가 두 additive migration을 연속 적용하게 한다. baseline raw SQL 재실행 및 schema 재생성은 금지한다.
4. `npx prisma migrate status`를 다시 실행해 두 migration 모두 적용됐는지 read-back한다.
5. 핵심 기존 데이터와 schema를 read-back하고, 이상 시 애플리케이션 배포를 중단한다.
6. migration 성공을 확인한 뒤에만 호환되는 애플리케이션 코드를 배포한다.

### 복구 절차

이번 migration은 nullable additive column만 추가한다. 승인된 rollback이 필요한 경우에만 백업·read-back 후 다음 형태의 명시적 SQL을 검토·실행한다. 자동 실행하지 않는다.

```sql
ALTER TABLE "Purchase"
  DROP COLUMN "foreignAmount",
  DROP COLUMN "customsDate",
  DROP COLUMN "customsExchangeRate",
  DROP COLUMN "baseAmount",
  DROP COLUMN "importVatBaseAmount",
  DROP COLUMN "importVat";
```

rollback은 외자 입력 데이터가 삭제되므로 사용자 승인과 백업 확인 없이 수행하지 않는다.

## 오늘 배포 장애 기록

- 원인: 환경변수 값 형식 문제
- 증상: WebSocket 연결이 실패하고 `wss://<앱도메인>/v2` fallback이 나타남
- 재발 시 확인 순서:
  1. 환경변수 이름·값 형식을 먼저 확인한다.
  2. 로그에서 WebSocket 연결 URL과 fallback 패턴을 확인한다.
  3. 앱 도메인과 `/v2` 경로가 예상값인지 확인한다.
  4. 원인 확인 전 반복 배포·롤백하지 않는다.
- secret·token·연결 문자열 원문은 로그나 문서에 남기지 않는다.
